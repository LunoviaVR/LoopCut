# LoopCut architecture

LoopCut is a Tauri 2 desktop app: a React/TypeScript editor UI on top of a Rust media engine.

```
Source ──FFmpeg child (decode [HW], crop+scale [GPU or CPU], CFR at source rate)──► NV12 / P010 / RGBA frames
   ──► FrameStore (RAM cap + LRU + disk spill) ──► Sequencer (speed, reverse, ping-pong, crossfade, holds)
   ──► Compositor (wgpu on the selected GPU or WARP): YUV→RGB, rotate/flip, tonemap, grade, LUT, captions
   ──► Preview (RGBA to the webview)  |  Export: gifski / FFmpeg palette / GPU dither, or FFmpeg video encoders
```

## Crates

| Crate | Responsibility |
| --- | --- |
| `loopcut-core` | Project model (`.loopcut`), migrations, Sequencer, geometry, GIF timing, media types. Pure, no IO. |
| `loopcut-media` | FFmpeg child processes (Job Object, `CREATE_NO_WINDOW`, protocol whitelist), ffprobe parsing, decode/encode command builders, proxies, thumbnails. |
| `loopcut-render` | wgpu compositor shared by preview and export; caption rasterizer. |
| `loopcut-export` | Export orchestration, GIF engines, video encoders, target-size search. |
| `loopcut-cli` | Headless driver for integration tests and batch use. |
| `src-tauri` | App shell: commands, custom protocols, settings, updater. |

Rust types are canonical; TypeScript bindings are generated by `ts-rs` into `src/ipc/bindings/`.

## Key rules

- FFmpeg is always a child process (never linked). Every input gets `-protocol_whitelist file,pipe` and
  `-noautorotate`; URL inputs are rejected. Children live in a Job Object with `KILL_ON_JOB_CLOSE`.
- Decoding is independent of output fps/speed: frames are decoded once at the source rate (again only when the frame
  store cannot keep a range, see Source frames); the Sequencer samples by source time.
- The same wgpu compositor renders preview and export. CPU mode runs the same shaders on WARP.
- Webview ↔ Rust media traffic uses custom protocols (`http://<scheme>.localhost/` on Windows) with opaque
  tokens minted by Rust — never filesystem paths.

## Source frames

Preview and export share one FrameStore. An export decodes each source range its plan needs into the store in one
pass, at the source frame rate capped at 60 fps. Whether a range fits is judged from its own frames only, so frames that
the preview or other ranges keep or lose do not make it fail. When a range does not fit, the plan's access order decides:

- **Forward plans** (source times never go back: plain playback) stream the range. A stream holds one frame, so memory
  stays flat. A request for an earlier time than the stream has read restarts it from the range start as a new decode
  pass. The Fast and GPU-dither engines depend on this: they sample the palette in order, then encode from the first
  frame.
- **Random plans** (reverse, ping-pong, crossfade) take at most two store passes: the store pass, and one refill when
  the store lost frames. A range that still misses fails the export as too large, and the error names the memory needed.

A streamed range therefore decodes once for its store pass, which stops when the store overflows, and once per traversal
of the plan. A hardware decode failure moves only the range that failed to the CPU chain, and that range keeps the CPU
chain for the rest of the export.

## Spike results (M0)

### (g) Hardware chains on the AMD Radeon RX 9060 XT (FFmpeg 9.0.2, BtbN gpl-shared)

| Chain | Result |
| --- | --- |
| `h264_amf` encode | OK at 256×256 and up |
| `hevc_amf` encode | **Fails at 320×240 and below**; OK at 640×360 |
| `av1_amf` encode | **Fails at 256×256**; OK at 320×240 and up |
| `-hwaccel d3d11va` decode + `hwdownload` + CPU `scale` | OK (8-bit and 10-bit) |
| `-hwaccel amf -hwaccel_output_format amf` + `vpp_amf=w:h:format=nv12\|p010` + `hwdownload` | OK (8-bit and 10-bit) |
| `h264_amf` decoder + `vpp_amf` | OK |
| `scale_d3d11` (after d3d11va) | **Fails**: `Could not create the texture (80070057)` |
| `-hwaccel vulkan` (+ libplacebo) | **Fails**: `VK_ERROR_UNKNOWN` allocating memory |
| `scale_d3d12` | Options are `w`/`h`/`format` (not `width`/`height`) — untested chain |

Consequences:
- Hardware encoders have **minimum frame sizes** that vary per codec and vendor. The capability probe must
  test several sizes and record each encoder's minimum; exports smaller than that fall back to CPU encoders
  automatically (GIF-sized MP4 loops are often below 640×360).
- The AMD GPU-scale path is AMF-native (`-hwaccel amf` + `vpp_amf`), not `scale_d3d11`. The probe must
  verify each decode+scale chain per adapter instead of assuming one works per vendor.
- Short-clip timings are dominated by AMF/D3D11 initialization (~300 ms); throughput is benchmarked on
  longer clips by the in-app probe.

### (b) Preview transport inside WebView2 (dev build, RX 9060 XT, raw RGBA + `putImageData`)

Environment: WebView2 / Edge 155, `isSecureContext = true` (dev origin `http://localhost:1420`),
`navigator.gpu` present with an AMD RDNA-4 adapter, WebCodecs present. (Production origin
`http://tauri.localhost` is re-checked on an installed build.)

| Method | 960×540 | 1280×720 | 1920×1080 |
| --- | --- | --- | --- |
| `Channel<InvokeResponseBody>` push | 123 fps (243 MB/s) | 72 fps (254 MB/s) | 28 fps (220 MB/s) |
| Custom protocol pull, 1 in flight | 66 fps | 42 fps | 16 fps |
| Custom protocol pull, 3 in flight | 107 fps | 69 fps | 27 fps |
| `invoke` → `tauri::ipc::Response` (latency p50 / p95) | 15 / 21 ms | 25 / 31 ms | 64 / 78 ms |

Decision: the v1 preview is rendered by the Rust compositor and delivered as raw RGBA —
**Channel push for playback** (capped at 1280×720-equivalent pixels, ~70 fps headroom) and
**`invoke` Response for single frames** (scrubbing, slider drags; ≤ 25 ms at 720p). Full-panel-resolution
frames are only requested when the playhead is idle. The ~250 MB/s ceiling makes in-webview WebGPU (now
known to be available) a worthwhile post-v1 optimization for 1080p+ playback.

### (a) wgpu GPU context and WARP fallback (wgpu 30.0.1)

Adapters found: `AMD Radeon RX 9060 XT` (DX12, discrete, driver 32.0.31041.1004) and
`Microsoft Basic Render Driver` (WARP, `DeviceType::Cpu`). Compute and render passes verified on both.
1920×1080 render + RGBA readback over 30 frames: **WARP 5.4 ms/frame** (render 2.0, readback 3.4),
**RX 9060 XT 3.0 ms/frame** (render 0.4, readback 2.6). WARP is fast enough to be the CPU fallback for
the compositor at GIF/loop output sizes.

DX12 shader compiler: no `dxcompiler.dll` ships with Windows or on `windows-latest`, so wgpu uses **FXC**.
All spike shaders compile with FXC. Decision: keep FXC for v1 (no extra 15 MB DLLs, no build-time downloads);
`static-dxc` was rejected because it downloads an unverified prebuilt binary at build time. Revisit if a shader
needs SM 6 features.

### (e) gifski 1.34.0

- API verified from source: `gifski::new(Settings{width,height,quality,fast,repeat})`,
  `Collector::add_frame_rgba(index, ImgVec<RGBA8>, pts)`, `Writer::write(w, &mut dyn ProgressReporter)`
  (returns only after the Collector is dropped). Lossy/motion/extra-effort are deprecated, doc-hidden
  `Writer` setters.
- Always pass explicit width/height: otherwise gifski auto-downscales frames above ~0.84 MP.
- Identical consecutive frames are merged (duration kept); its denoiser can also drop near-identical
  frames on noisy content (total duration preserved, per-frame delays not uniform).
- The last frame's delay is the previous interval unless pts are built with the "exact delays" rule
  (`pts_for_exact_delays`).
- `lossy_quality` below 100 is not monotonic on synthetic noise (99 is ~7% *larger*); only low values
  shrink files. The UI treats 100 as "off" and is tuned on real footage in M5.
- `extra_effort` costs ~1.7× time for ~2% size → off by default.
- Speed (test profile): 480×270, 100 frames, quality 90 → ~40 fps with extra effort, ~68 fps without.

### (f) Captions (cosmic-text 0.19 + swash outlines + tiny-skia 0.12)

Outlines come from `SwashCache::get_outline_commands` (y-up, flipped for tiny-skia). Stroke is drawn at
2× width under the fill so exactly `width` shows outside (correct for opaque fills; translucent fills
need a layer — M4). Color emoji works through COLR (Segoe UI Emoji). Impact resolves from system fonts.
Warm raster of a 64 px two-line caption ≈ 25 ms (test profile) → rasters are cached per text+style.

### (c) Range requests on files larger than 4 GiB (server side)

`loopcut-media://` keeps every offset and length in `u64` and reads one bounded slice per response.
`protocol::tests::ranges_past_four_gibibytes_are_served_exactly` serves a 5 GiB sparse file: an open range starting
at 4.5 GiB returns 206 with `Content-Range: bytes 4831838208-4836032511/5368709120` and the exact bytes, and a suffix
range returns the last 4 bytes. Still open: watching a real `<video>` seek inside such a file in the installed app
(WebView2 network log), which needs a large real video and is part of the release smoke test.

### (d) Installed NSIS build (0.0.1, Windows 11, RX 9060 XT, WebView2 155)

The 60 MiB per-user installer (`/S`) puts `loopcut.exe`, `uninstall.exe`, `ffmpeg/<version>/` and `licenses/` in
`%LOCALAPPDATA%\LoopCut`, registers the uninstall entry and the `.loopcut` association, and adds Start menu and desktop
shortcuts. The installed copy differs from `target/release/loopcut.exe` only in the 3-byte bundle-type marker
(`NSS` vs `UNK`) the updater reads.

- The self-test passes 19/19 from the install folder with the production CSP; FFmpeg resolves from
  `%LOCALAPPDATA%\LoopCut\ffmpeg\<version>\`.
- No console window: across 58 ffmpeg/ffprobe children, no visible window appeared for a child or its console host.
- Job Object: killing `loopcut.exe` while an `ffmpeg.exe` child decodes leaves no child alive 0.5 s later.
- Update-style reinstall (`/P`, passive) while the app is decoding: the installer closes the app (its children go
  with it), removes a stale `ffmpeg/<old>/` folder through `windows/hooks.nsh`, keeps the current FFmpeg files
  byte-identical, and finishes in 8 s with exit code 0.
- Not covered here: the updater's own download, signature check and relaunch, which need a published release.

Testing note: processes started from an MSIX-packaged host (for example a sandboxed terminal) have their AppData and
HKCU writes redirected into that package, so an install made from there is invisible to the user. Run installer tests
from a normal shell or Explorer.

## Measured performance (wave 1, RX 9060 XT unless noted)

| Path | Result |
| --- | --- |
| Compositor 1920×1080 NV12 → 1920×1080 RGBA (render + readback) | 3.0–3.2 ms/frame |
| Compositor 3840×2160 NV12 → 1280×720 preview | 3.1–3.2 ms/frame |
| Compositor 1920×1080 → 480×270 (GIF size) | 0.6 ms/frame |
| Same on WARP | 230 ms (1080p→1080p), 240 ms (1080p→480×270), 15 ms (480×270→480×270) |
| Proxy 1080p60 → 720p H.264, libx264 veryfast | 10.4× realtime |
| Proxy 1080p60 → 720p H.264, h264_amf cqp 23 | 7.8× realtime (3.4× larger files → use a bitrate cap for proxies) |
| gifski 320×180 lossy 100/80/50/30/10 | 100% / 98.5% / 67.6% / 62.6% / 64.1% size (non-monotonic below ~30) |

WARP's cost tracks **input** size (queue uploads run at ~11 MB/s on WARP), not output size. Export decodes
at output size (FFmpeg crops/scales first), so CPU-mode GIF exports stay fast; CPU-mode preview must decode
at reduced resolution (≤ 640 px wide) to stay interactive.

FFmpeg facts verified while building the media layer:
- `-ss` with `-seek_timestamp 1` seeks in absolute stream time (needed when a stream does not start at 0).
- Transcodes copy the source display matrix: proxies that physically rotate frames must reset it with the
  input option `-display_rotation:<idx> 0`.
- libx264 ignores output-side `-color_primaries/-color_trc`; tag via `setparams` on frames.
- FFmpeg's native VP9 decoder drops alpha; VP9 WebM with `alpha_mode=1` must use the `libvpx-vp9` decoder.
- ProRes 4444 decodes as `yuva444p12le`.
